## Architecture rules
- Domain logic lives in `src/domain/` as mutate-a-draft functions that throw `DomainError` before mutating; the server runs them (src/lib/garden.server.ts) and the UI only sends typed commands via `GardenStore.cmd` — keeps validation/ownership in one testable place.
- Cloud is the source of truth: all writes go through the service-role-only `garden_commit` RPC with optimistic versioning, and `cycle_runs(agent_id,bucket)` uniqueness stops duplicate cycles; clients read via public/owner-scoped RLS — keeps funds atomic and owner-checked.
- Scheduled cycles hit `/api/public/garden/tick`, authenticated by a server-only secret header (the browser key is not enough) — the browser key is public.
- Garden agent balances and trading remain virtual through `ChainAdapter`. The separate PQ launchpad uses real Meteora DBC SDK transactions, gated by cluster/genesis, config and pinning readiness; no Fleuri custody program is required for provenance. Never label a pending signature or migration flag as a verified launch or DAMM v2 pool.
- PQ private keys stay in browser memory and encrypted backups. Owner writes go through authenticated server functions and service-role-only atomic RPCs. Persist signed transaction bytes before broadcast; retries must keep the exact message and signature. Public verification must re-check dual registration signatures, Memo anchoring, all signed config terms, confirmed transaction, mint authorities and immutable pinned metadata.
- All colors/fonts come from tokens and `@utility` classes in `src/styles.css`; flower motion is CSS keyed to a wall-clock `--fl-delay` so every tile sways in phase.

- Meteora DBC configs are created through `/launch-config` as an owner-reviewed, wallet-signed `chain_preparations` kind `config`; the config key is browser-generated and confirmation compares the on-chain account to the reviewed draft — no custodial wallet or silent recipient.
- The client build must never stub Node builtins: rolldown's native resolver externalizes `node:buffer` before `resolve.alias` applies, so `vite.config.ts` pins `buffer`/`node:buffer` to the real feross `buffer` package with a build-only pre `resolveId` hook (dev pre-bundles `buffer` via optimizeDeps, because the raw CommonJS file has no ESM export) — without it safe-buffer/bs58/Solana SDK crash on hydration in production. The same hook pins `bigint-buffer` to its `dist/browser.js` build, because rolldown misses its `browser` field mapping and the Node entry crashes the browser bundle with `__filename is not defined` when signing.
- Botanist reports are sold only through x402 V2 exact at `/api/public/botanist/report`; orchestration lives in pure `src/lib/botanist-flow.ts` (deps injected) and the report in `src/lib/botanist-report.ts`. Payer signatures are Ed25519-verified and the facilitator verifies before the payment is atomically bound; the facilitator's signature is stored as a frozen candidate before chain reads; delivery requires that transaction's message hash to equal the accepted payment and the exact credit at its canonical destination account index. The browser saves the exact PAYMENT-SIGNATURE before the first POST and only resends it. This lets a buyer retry without being charged twice or receiving a report that wasn't paid for.
- Browser code must not import `@solana/spl-token`, because `spl-token-metadata` touches a global `Buffer` at import and breaks hydration. Use the tested minimal helpers in `src/pq/botanist.ts`.
- Pollen accounting uses the program's Q64 `feePerShare` checkpoint math (`claimable` in `src/pq/pollen.ts`), not the SDK's lifetime-funds approximation, so displayed claimable amounts match what the program pays.
- Botanist /settle calls carry a stable per-job `Idempotency-Key` (the job's request_hash), and each job's facilitator URL, accepted requirement and resource are frozen at quote time; retries after binding never re-run /verify — they recover the known candidate, the chain message hash, or replay the identical /settle body, else stay pending. This lets a retry get the same receipt without the buyer paying twice.
- Botanist job access is authorized only by the off-chain capability (job id + raw token checked against `capability_hash`): via body jobId/token, or for generic x402 retries via `accepted.extra.botanistJob/botanistCapability` that only the quote's 402 advertises. The token is never stored in plaintext nor sent to the facilitator (the frozen requirement stays byte-stable). The job memo is public on chain, so it is cross-checked only and never authorizes.
- Pollen Staking is a separate Anchor workspace in `onchain/pollen-staking` with integer accounting in `math.rs`. The app mirrors its layout in `src/pq/staking.ts`, cross-checked against the generated IDL and a Rust-written fixture. Deposits are gated by `readiness()` on live chain facts. This means the UI can never enable deposits for an undeployed, mismatched or freezable setup.
- Greenhouse Trials run pure `src/domain/greenhouse.ts` over the shared `runCycle`: each participant gets its own clone of one frozen sanitized market, and an external shock tape is seeded only by seed/scenario/repetition. Runs are created and finalized through service-role-only `greenhouse_*` RPCs, keyed by (owner, request_id), and retries reuse the stored frozen inputs. Replay re-executes the bundle and compares exact hashes, and an engine version change must bump `ENGINE_VERSION`. This keeps results reproducible, independent of selection order, and impossible to overwrite silently.
